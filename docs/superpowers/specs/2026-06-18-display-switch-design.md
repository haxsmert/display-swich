- 日期:2026-06-18(2026-06-22 修订:统一模型 + 死锁安全模型定稿 + 机型感知 + 架构自检)
- 状态:**v1.0 已完成、真机走查通过**(列表/系统名/关一块/最后一块灰显/关内建留外接/恢复/编号稳定 全过);机型感知保护 + 死锁加固 + `isSupported`(私有符号 + Apple Silicon 架构)自检 + app 图标 均已落地
- 目标平台:Apple Silicon(M 系列)+ macOS 13+;非 Apple Silicon 由 `isSupported` 判不支持(只读)
- **验证环境(实测标注按此读)**:Apple Silicon(M 系列)。**2026-09-15 起为 macOS 27.0**;此前为 macOS 26.x(26.5.1 → 26.6.2)。
  ⚠️ 文中凡标「实测」的结论,**日期在 2026-09-15 之前的跑在 macOS 26 上,之后的跑在 macOS 27 上**。
  本 app 依赖私有符号与 IOKit 内部结构,**跨系统大版本不保证行为一致**——已有一例疑似因此改变(见 §7.5)

## 1. 背景与目标

Mac 外接双显示器场景下,希望用一个**极简**的菜单栏小工具,**软件层面关闭或打开某块显示器**——做到 BetterDisplay 的「断开/重连」核心效果,但不要它的复杂度和付费。

「关闭」的明确定义:**虚拟断开**——让 macOS 以为该显示器被拔掉(从活跃显示器列表消失、窗口自动迁移到另一块屏、菜单栏/Dock 重排),「打开」时再让它干净地回来。不是熄背光、不是镜像切换。

### 统一模型(一句话讲清)

菜单列出**所有活跃屏(含内建屏)**,显示名同系统设置(同型号屏带系统的 (1)(2),关掉其一号不消失;说明行写序列号尾号)+(主);任意屏都可关,但**绝不把用户置于「无法恢复的全黑」**——保护规则见 §7(机型感知:有内建屏的笔记本允许关到全黑、靠开盖恢复;无内建屏的台式机必须至少留一块活跃屏)。

> 演进说明:早期按「左/右」命名;2026-06-22 重构为统一模型(内建屏纳入菜单、UUID 稳定编号),中途一度简化保护为「至少留一块活跃屏」,后又按真实使用场景**升级回机型感知**(笔记本合盖用外接、关光外接靠开盖恢复内建)并加死锁加固。本文档已按最新状态描述。

## 2. 可行性验证结论（已完成 / 已真机复验）

在开发机(Apple Silicon / macOS 26.5.1 / 两块同型号 4K 外接屏 + 内建屏)上验证:

- **只读探测:** 能可靠枚举所有屏并分清主/副/内建;关键私有符号 `CGSConfigureDisplayEnabled` 在 macOS 26 上存在;公开恢复兜底 `CGRestorePermanentDisplayConfiguration` 也在。`CGDisplayCreateUUIDFromDisplayID` 需 `import ColorSync`。
- **断开+恢复实测:** 对非主屏、对内建屏(即便它当前是主屏)执行 `.forAppOnly` 断开 → 活跃屏减少(真的从系统消失);恢复 → 干净回来。`.forAppOnly` 的断开**全局生效**(窗口迁移、活跃屏减少),已实测确认。

**结论:纯自研「真·断开」在该平台可行**,不需要 BetterDisplay、不需要关 SIP、不需要特殊 entitlement(开发者签名即可运行)。

⚠️ 平台限制:此结论依赖 Apple Silicon + 较新 macOS。Intel 平台不在目标范围。**已加架构自检**:`isSupported` 要求 `hw.optional.arm64 == 1`,非 Apple Silicon 一律判不支持(只读不动屏);加之 app 实为 arm64-only、Intel 根本无法启动,双重保证不在未验证平台上动显示器。

## 3. 非目标（YAGNI,本期不做）

- **开机自启动 —— 永不做(这是安全约束,见 §7,不是临时取舍)**
- **记忆/持久化上次的开关状态 —— 分两层,都不做,但性质不同:**
  - **落盘持久化(跨 app 重启)= 硬安全约束,永不做。** §7.2 的逃生链条依赖「重启后 = 所有屏正常 +
    app 未运行」。若 app 记住状态并在启动时照着关屏,用户强制重启逃生后一开 app 又黑,命脉即断。
    与「永不开机自启」同级。
  - **运行期意图记忆(app 退出即忘)= 产品取舍,2026-09-07 评估后决定不做。**
    场景:拔坞时救援把屏全开回来,插回坞后不记得之前关过内建屏,要手动再关一次。
    评估过两个替代方案(插回后自动关回去 / 菜单给一项手动「恢复上次布局」),
    都不违反上面的安全约束、工时也不大,仍决定**维持现状**——
    保住「关屏是**瞬时动作**、救援之后即回到干净状态」这个模型的简单性,
    不引入「程序替用户保管意图并择机自动关屏」的新状态。代价是插回坞后手动重关一次,已接受。
  - 重估的触发条件:插拔频率显著上升、手动重关成为明显负担时,再按「意图模型」重新设计。
    (认屏不是障碍:实测每块屏的 EDID 带唯一序列号,**同型号的两块屏序列号也不同**。)
- 全局快捷键 / 急救快捷键
- 自动触发(如插电源/接屏时自动切)
- ~~拔屏自动恢复守护~~ → **2026-09-07 改为实现**(真实事故驱动)。当初的证伪只覆盖 CoreGraphics 那两条路,
  今天实测确认那两条路确实不可用,但**内核事件是第三条路**,实测可靠。见 §7.3
- 显示器重命名
- 熄背光/亮度/DDC 控制 / 创建虚拟显示器 / Intel 平台支持

以上都不实现。需要时再开新一轮设计。

## 4. 架构总览

一个 macOS 菜单栏常驻应用(`LSUIElement = true`,无 Dock 图标、无主窗口),Swift + AppKit + SwiftUI,**零第三方依赖**。

交互(v1.0.17 起):点菜单栏图标 → 弹出面板(点面板外自动收起)。顶部一句摘要(「3 块屏 · 2 块亮着」);
每块屏一张卡片(含内建):名称、说明行(内建 / 外接 · 接法 · 分辨率与刷新率,关着时写「已关闭」);**点整行切换**,开着浅蓝底、关着普通底;
开关被锁住时卡片里直接写原因;底部是全黑救援状态(点开救援日志)、版本号(点开仓库)、「退出」。
版式借鉴 MonitorBar;配色跟随系统外观、只用系统语义色(浅色、实底,不做透明)。
v1.0.16 及以前是原生 `NSMenu`,每块一行带勾选。

v1.0.18 按他用下来的反馈改了三处(都经他真机复现、日志核对):
- **整行就是开关,没有任何开关控件**(他的要求;状态看行首圆形图标,关着的行说明行写「已关闭」,不只靠颜色;
  文字不因开关变淡——Wi-Fi 菜单里没连上的网络也是同样的黑字)。
  中间一版留了一个只显示状态的开关图形,他指出看上去仍是按钮,已去掉。v1.0.17 用系统开关控件把「目标值」传给逻辑层,
  实测它自己记的状态落后一步,打开面板后第一下传回的总是当前值,于是第一下没反应;
  现在界面不保存任何开关状态,点哪行就「翻转哪块」,开还是关由 Core 按系统真实状态当场决定。
- **面板是自管窗口,不再用 NSPopover**。开关主屏时 macOS 会把菜单栏连同图标搬到新主屏,
  NSPopover 随之被系统收起,收起动画还按旧坐标播放(实测:开关内建屏每次都收起,开关非主屏不收起)。
  自管窗口只在点面板外、再点图标、切到别的 app 时收起;图标挪到哪,面板跟到哪
  (监听图标所在窗口的移动 / 换屏,实测主屏切换时图标会先后落在 3 个位置、约 60 毫秒内落定)。
  不激活本 app,打开面板不抢当前 app 的焦点;关掉系统的「退到后台自动隐藏」,收起时机全由我们定。
  **按 Esc 收起**:他用真键盘按,能收起(2026-10-23)。但**脚本合成的 Esc 测不出来**:从另一个进程发的合成按键
  一律交给系统认定的前台 app(访达在前台做最小实验,不激活本 app 的键窗口、主动 `NSApp.activate()`、走「展开界面」会话、
  会话开始时再请求激活,四种都收不到);进程**自己**发的合成按键又会回到自己手里,拿它做实验会误判。
  所以 Esc 只能真机手按验收;脚本测试时发 Esc 之前先把焦点挪到桌面,免得落进他前台的程序。
- **macOS 27 起开 / 关走系统的「展开界面」会话**(`NSStatusItem.expandedInterfaceDelegate`):系统为不用 NSMenu、
  自己摆窗口的菜单栏图标提供的正式做法。会话开着时系统给图标画上与 Wi-Fi 等系统菜单相同的高亮底——
  自己调 `highlight(true)` 在 macOS 27 上画不出来(同步、异步、改按钮类型都试过)。实测会话的行为:
  点图标开会话;会话中再点图标,系统什么都不做(不结束、不回调),由我们收起——按下时刻晚于会话开始的那次点击才算,
  打开面板的那一下系统处理完才转给我们,按下时刻早于会话开始;我们自己收起时取消会话;
  **主屏切换(菜单栏搬家)时会话不断**,面板与高亮底一起跟到新主屏(点亮 / 关掉内建屏各测一次)。更早的系统照旧接点击。
- **外形与位置照菜单栏 Wi-Fi 菜单**:纯圆角矩形,圆角 13pt;左缘对齐图标的高亮底(即图标窗口左缘),
  上缘贴着菜单栏下沿(取这块屏可见区域的上缘;图标窗口上下各比菜单栏多出 1~2pt,不能拿来当下沿)。
  曾照 AppKit 系统菜单(弹一个临时状态栏菜单实测)左偏 5pt、比图标窗口下沿再低 2pt,比 Wi-Fi 菜单低了 4pt——
  Wi-Fi 等控制中心那一套与 AppKit 菜单不同,他指定以 Wi-Fi 为准(2026-10-23)。
  中间一版加过指向图标的箭头(他当时嫌面板离图标太远、建议加),他看过后改为「和 mac 一样的纯矩形」。
- **布局在交互中不动**:每行高度固定;锁住原因写在顶部提示区,被锁的那行只在行尾多一把小锁。
  他指出:只剩两块屏时开关副屏,剩下那块多出一行提示,面板长高、整体弹跳——打乱了他接下来要点的位置。
  提示放顶部是他的设计。提示区**平时空着**:曾在那里报数「3 块屏 · 2 块亮着」,他指出没用——
  每行行首的图标已经写明开没开。**不用鼠标悬停提示**(他认为低级)。
  顶部的锁形图标嵌在文字里排版:单独摆一个图标会把这一行撑高 1pt,面板照样会跳(截图实测)。
- **被锁住的那一行再点,要有反应**(他的要求):行尾的锁与顶部提示一起左右抖一下(macOS 输错密码时登录框那种抖法,
  只是绘制偏移,不动排版)。所以被锁的行不设成不可点,只是没有鼠标经过的高亮——高亮表示「点了会切换」。
  切不切仍由 Core 定:点击照常交给 Core,没切成且这块屏正被锁住,才算一次被拒。
- **说明行写电脑端的口**:「外接 · 雷雳 1 · 3840×2160 · 60Hz」(他的要求,2026-10-23),写法「雷雳 N / USB-C N / HDMI」。
  对应关系读系统的显示交换器(`display-crossbar0`):每块屏的显示控制器(`disp0` / `dispextN`,由 CoreDisplay 私有符号
  `CoreDisplay_DisplayCreateInfoDictionary` 给出)背后的协处理器(`DCP` / `DCPEXTn`)占着交换器哪个上游口、被路由到哪个端口的哪条通路,
  通路节点上写着机身端口号、类型、是否雷雳隧道(细节与实测见 `MacPort.swift`)。按控制器对应,同型号、EDID 完全相同的屏也不会对错——2026-10-23 在 MacBook 上证实:两块同型号屏一块直插 1 号口、
  一块经插在 3 号口的拓展坞,分别写「雷雳 1」「雷雳 3」;把其中一块单独切到 30Hz,只有它对应的控制器时序跟着变。
  读不到就不写,不猜;关着的屏不写口。
  走过的弯(2026-10-23,Mac mini M4):起初把交换器 `ufp-endpoints` 名单的序号当上游口编号、只认 `dispextN`,
  在 MacBook 上看着对,换到 Mac mini 机身 HDMI 就读不出口——那里外接屏由主协处理器经 `disp0` 输出,名单序号也与协处理器错位,
  节点还省略了 domain / port(内核按 0 处理)。现在上游口按协处理器节点自己声明的编号对。
  走过的弯:曾写一个「雷雳」(2026-10-22),他指出不准——读起来像在说显示器那头的线(他的两块屏在显示器那头一块插 DP 线、
  一块插 USB-C 线),而且当时只会按 EDID 对应,同型号两块屏对不上是哪块,于是撤掉不写。现在写明是 Mac 上的几号口。
  显示器那头接的什么口不写:DDC/CI 查询 VCP 0x60 读得到当前输入源(实测两块屏分别报 DisplayPort-1、DisplayPort-2),
  但编号由厂商自定、还要每次向显示器发查询,他判断意义不大。接口路径仍原样写进诊断,排查时用。
- **样式照抄菜单栏 Wi-Fi 菜单**(他先后指出「很廉价」「浅蓝边框 + 底色超级土,像二三十年前的后台管理系统」,
  后来把 Wi-Fi 图标放出来,要图标、动效、锁等都照它):行没有底色、不描边,状态只由行首圆形图标表达。
  对照方法(2026-10-23):临时垫一块纯白窗口在 Wi-Fi 菜单与本面板背后,两边截图比颜色、尺寸与「墨量」;
  候选字号 / 字重 / 颜色先在同样的系统玻璃上画出来,挑与 Wi-Fi 完全对得上的那一组。颜色只认截图——
  录屏帧有颜色转换(同一块悬停底,截图 234、录屏 229),不能拿来比。量出来的规格(macOS 27):
  - 行首圆 26pt,离面板边缘 14pt;开着是系统蓝 `systemBlue` (62,136,249)——强调色选「多色」(默认)时
    Wi-Fi 用的就是它,`controlAccentColor` 是另一种偏深的蓝 (55,123,249),曾用它;用户选定别的强调色时随强调色
    (Wi-Fi 那时的样子没实测,不去改他的系统设置,按「多色」的含义推定)。关着是 `secondarySystemFill` 浅灰圆。
  - 圆里的图形是 13pt 粗体的系统符号(Wi-Fi 扇形在这个字号字重下尺寸与墨量都对得上,曾用 12pt 中等);
    开着白色,关着主文字色(浅色下纯黑,同 Wi-Fi;曾用灰色,看上去像不可用)。
  - 名字 13pt 常规体、控件文字色(最深处 (38,38,38),不是纯黑;曾用中等字重);圆到文字 8pt(曾 12pt)。
  - 锁是 13pt `lock.fill`、次要色,尺寸 9×12.5pt、颜色、墨量都与 Wi-Fi 的锁吻合(曾 11pt);右缘离面板边缘 16pt。
  - 两行字(名字 + 说明行)照系统菜单项自带的「副标题」(`NSMenuItem.subtitle`,弹临时菜单实测):行高 36pt,
    两行顶到顶 15pt,副标题 `secondaryLabelColor` (128)。曾是 46pt、行间多 2pt、说明行偏浅,比原生松散。
  - 鼠标经过时整行一层 `secondarySystemFill` 圆角底(真实背景上 (251,251,255) → (231,231,235),纯白垫底上 254 → 234,
    两种背景都与 Wi-Fi 相同),离面板边缘 7pt、圆角约 11pt,图标与文字不变,出现与消失都没有过渡;
    分隔线两头缩进 14pt。走过的弯:先是 6% 的灰、边距圆角都没对齐(他:「不明显」),
    再是系统文字菜单的强调色蓝底、文字反白(他:「太怪异」)。
  标题写软件名 DisplaySwitch(他的要求,不写中文);曾叫「显示器开关」(他嫌土),后取系统的叫法「显示器」。
  右上角提示区用系统菜单副标题的样式(11pt、`secondaryLabelColor`,与说明行一致),锁用 SF Symbols 跟随文字的默认大小、
  与汉字同高;曾用更浅的次要色、锁缩小一号,锁比汉字小一圈、整句发虚(他指出要优化)。
  锁与文字并排、按中心对齐,提示与标题也按中心对齐(实测各差 0.25pt)。曾把锁嵌在文字里、整行按基线对齐:
  符号按西文字母的高度排,锁比汉字高 0.75pt;小一号的汉字又比标题低 1.25pt(他指出没对齐)。
  系统的 `Label` 也能对齐,但图标与文字隔 10pt,像两样东西,没用。
  **宽度按内容定**(曾固定 320pt,他嫌太宽),开关屏、主屏转移时会变的文字(主屏标记、开回来后的分辨率、
  锁住提示)都按最长的写法预留,所以点来点去面板不变宽;只有屏幕增减时才会变。
  **底部是一条状态栏**(取法 WhatCable 的底栏,他的建议):左边是**显示驱动状态**(他的建议),右边「v1.0.18 · 退出」。
  驱动状态只认两条有实测依据的信号(`DriverHealth`):① 卡死——系统日志里 `AppleThunderboltDPOutAdapter`
  报 `evaluating for > 1m`(卡死那天任意 2 分钟约 1200 条,重启后健康的 3 小时 0 条,出现就算);
  ② 残影屏——在线的外接屏比物理连接多,隔 3 秒复核(插回时在线数比物理数早约 1 秒恢复)。
  被本 app 关掉的屏可能还插着、也可能已拔走,分不出是哪块,所以不拿它抵扣:宁可漏报混合情况,不在健康时误报。
  打开面板、屏幕增减时检查(读日志约 1 秒,在后台);读不到日志(非管理员)显示「无法检查」,不说正常。
  点状态那一组弹出开发者工具(系统菜单):驱动检查的依据与「重新检查」、救援状态与上次触发时间、
  打开救援日志、复制诊断信息,条目固定,不随记录增多而变长。「全黑救援已就绪」曾常驻底部,他指出会误导,挪到这里。
  **面板底直接用系统的材质组件,不自己画**(他的要求:用 mac 官方组件,保持原生风格,并随系统的玻璃 / 透明度设置

## 5. 显示器开/关机制

私有符号通过 `dlsym(RTLD_DEFAULT, ...)` 解析后 `unsafeBitCast` 成 `@convention(c)` 函数指针调用,避免链接期硬依赖。

```
CGBeginDisplayConfiguration(&cfg)
CGSConfigureDisplayEnabled(cfg, displayID, on)   // 私有符号
// 失败:CGCancelDisplayConfiguration(cfg) 回滚,不泄漏事务
CGCompleteDisplayConfiguration(cfg, .forAppOnly)
```

### 退出恢复策略（关键安全决策）

目标:**app 退出或崩溃时,所有被关的屏自动恢复**,永不出现「屏黑着却恢复不了」的死局。

> ⚠️ 本节曾把「进程退出由系统自动回滚」写成已实测结论,2026-08-31 实测**推翻**。以下按「实测 / 推断」分别标注,勿再混写。

- **恢复由 app 自己做,系统不代劳**。`CGSConfigureDisplayEnabled` 是一次性状态写入,写完就与调用进程无关。
  - **实测**(M 系列 · macOS 26):裸进程关屏后立即退出,10 秒后该屏仍是断开的;另一个进程可以把它重新点亮。故断开状态**不绑定**在调用进程上,`.forAppOnly` 在这个私有调用上**不提供**「进程退出即回滚」。
  - **实测**:`.forAppOnly` 下断开仍全局生效(这是本条唯一被早期验证过的部分)。
- **正常退出**:`applicationWillTerminate` → `restoreAll()` **主动** re-enable 所有被本 app 关掉的屏。这是日常恢复的唯一实际路径。
- **崩溃 / `kill -9`**:`restoreAll()` 来不及执行,屏会保持断开,**无系统兜底**。逃生靠下面的重启路径。
- **重启可恢复**(逃生路径的依据):
  - **实测**:关屏只会改写 `/Library/Preferences/com.apple.windowserver.displays.plist` 里显示器配置块的**先后顺序**(把关掉的挪到末尾),两份文件各自排序后差异为 0;该文件中**不存在** `Enabled`/`Disabled`/`Active` 之类字段。即断开状态**没有落盘**,只活在 WindowServer 内存里。
  - **推断(未经一次真实重启实证)**:重启后 WindowServer 内存清空并重新枚举硬件,屏应恢复点亮。配合「永不开机自启」,重启后必为干净状态。
  - **实测**:app 进程死 ≠ WindowServer 死——两者是不同进程,kill app 不清空 WindowServer 的状态,故**崩溃与重启效果不同**,不可混为一谈。
- `CGRestorePermanentDisplayConfiguration()` 于启动时调用一次(历史兜底,对上述私有调用**未观察到**效果)。
- **绝不使用 `.permanently`**(那是「断开后无法用代码恢复」死坑的来源)。

### 7.4 数据源:系统是权威,记账只管身份(2026-09-18,v1.0.12)

**事故**:关掉一块外接屏 → 拔线 → 插回来 → 那块屏从菜单里消失,既不在活跃列表也不在记账里,
彻底失联,最后靠私有接口枚举才捞回来。

**根因是职责错配**:app 一直用**自己的内存记账**去推断系统状态,记账既当「有哪些屏」的依据、
又当「这屏叫什么」的依据。而记账在两种情况下必然失效——进程死掉(崩溃 / 强杀 / 注销),
以及为了清幽灵项而主动删除记录。一旦失效,被关闭的屏就成了孤儿:
**被关闭的状态留在 WindowServer 里不会自己恢复,而它跟着显示器走、不跟着线走。**

同一个建模问题此前已经以四种面貌出现过:事件源选错(§7.3)、判据滞后(§7.3)、
触发时机不全(§7.3)、状态归属错(本节)。四个 bug 是一个设计。

**改法 —— 两者职责分开:**

| 职责 | 依据 | 理由 |
|---|---|---|
| 有哪些屏、哪些亮着 | **系统枚举**(`CGSGetDisplayList`) | 它是唯一能列出**被禁用显示器**的接口;公开的 `CGGetOnlineDisplayList` 看不到它们(实测:被关掉的屏从 online 列表一并消失) |
| 这块屏叫什么、编号是几 | **本 app 的记账快照** | 被禁用的屏连 UUID 都解析不出,系统枚举给不出名字;同型号屏的稳定编号(如「某型号 (1) / (2)」)只能靠关闭前存下的快照维持 |

- **启动兜底**`reviveOrphanedDisplays()`:直接问系统要「存在但没点亮」的屏,全部点亮。
  此刻记账必然是空的,系统里任何未点亮的屏都是上次遗留,点亮既安全又符合
  「app 启动即回到干净状态」的既有语义(§7.2 的逃生链条依赖它)。
- **运行期**:记录始终保留,菜单渲染时按物理连接数决定显不显示——
  拔走不显示(不留幽灵),插回来重新显示(不失联)。**绝不再用删记录来实现隐藏。**

**判据只剩一个**:物理连接真相统一用**带 EDID 的传输节点计数**。
原先还有一个 framebuffer 判据(数 `DisplayWidth` 键),**已于 2026-09-18 删除**——它有两个致命缺陷:
拔线时**滞后约 3.5 秒**才归零(救援恰好发生在那一刻,拿它判断等于不救),
以及**数不到被禁用的屏**(屏一被关 `DisplayWidth` 键就消失,两块屏关掉其一时它报 1、EDID 判据报 2)。
后者曾把一块还连着的屏从菜单里藏起来。而它的文档一直写着「不受本 app 软件断开影响」,
正是照着这句假承诺选错了判据——**留着一个「文档说 A、实际做 B」的方法就是持续的陷阱,故整个删除**。

**已知限制(实测)**:枚举出的候选里混着**空槽位**(没接屏的接口),它们与真实被禁用的屏
在这一层完全同形(都是 1×1、非活跃),**无法区分**。唯一分辨方式是挨个尝试点亮:
真屏 0.5 秒内成功,空槽立刻返回错误 1001,**都不阻塞**,所以逐个试是安全的。
合盖时的内建屏不计入——它此刻不活跃是正常的,且对它调点亮会阻塞约 20 秒。

### 7.5 系统升级是本 app 的主要风险源(2026-09-20)

本 app 依赖的东西**都不在 Apple 的兼容性承诺内**:私有符号 `CGSConfigureDisplayEnabled` /
`CGSGetDisplayList`、IOKit 的 `IOPortTransportState` 节点与 `EDID` 键、`IOPMrootDomain` 的
`AppleClamshellState`。系统大版本升级后它们可能消失,**更隐蔽的是符号还在、行为变了**。

**升级后执行**:`bash scripts/selfcheck.sh`;手边有外接屏时再跑 `bash scripts/selfcheck.sh --plug`,
按提示拔一块屏,复验拔线通知这条驱动内部行为(见 §7.3「机制」)

它拼接**产品代码本身**来跑(不另写一套检查逻辑,否则验的不是真实路径),
且不只查「符号在不在」,更查「行为对不对」。**2026-09-20 在 macOS 27.0 上全部通过。**

#### 一例疑似由升级引起的行为变化(**存疑,未能证实**)

| 时间 | 系统 | 关于 framebuffer 判据(`DisplayWidth` 键)的实测结论 |
|---|---|---|
| 2026-08-31 | macOS 26.x | 「软件关掉后 IOKit 仍报 1 条连接」——即**能**看到被禁用的屏 |
| 2026-09-18 | macOS 27.0 | 「屏一被禁用 `DisplayWidth` 键就消失」——即**看不到**被禁用的屏 |

两条结论直接矛盾,而 macOS 27.0 的安装日期(2026-09-15)正好夹在中间;
用户也反馈「之前都是好的」。但**无法证实**,因为:
已经无法回到 macOS 26 复测;而且 2026-08-31 那次实测本身可能就不严谨——
同一天同一处判据还栽过「只接一块外接屏时错判据碰巧给出正确答案」的跟头(见 v1.0.3)。

**两种解释都可能,故记为存疑。** 真正的教训与哪种解释无关:
**依赖系统内部结构的结论有保质期,系统升级后必须重测,不能靠继承旧结论。**

## 6. 显示器标识与命名

- **稳定标识优先用显示器自带的序列号文本,其次 UUID**:同型号屏的 vendor/model/数字 serial 可以完全相同(他的两台都报 19),
  但 EDID 里的序列号文本每台不同(2026-10-23 实测只差末位),从 CoreDisplay 给的控制器位置上
  `DisplayAttributes.ProductAttributes.AlphanumericSerialNumber` 读。**UUID 不是持久标识**:这类屏系统按接法分 UUID,
  换口就可能换一个(显示偏好里这一型号累计 10 个 UUID,显示器只有两台;他换口后发现同一台从 (2) 变成 (1))。
  `displayID` 也会随重连变化(实测见过 2↔5 互换;同一天 id 4 先后给了两台不同的屏)。序列号用来排序,界面只写尾号,不写进日志与诊断。
  走过的弯:原先写「同型号屏 serial 完全相同、UUID 重连后稳定」——只看了数字序列号,也没在换口时核对过 UUID。
- **菜单显示名 = 系统设置里的名字 +(主),号不随开关消失;同型号屏说明行写序列号尾号**(他的决定,2026-10-23)。
  - **号**:同型号屏要带号,用户才能和系统设置里的屏对上(他:「不然用户怎么和系统设置里的屏幕对上」)。两块都亮着时照抄系统此刻的号;
    系统的号是「动态消歧」,关掉同名的另一块,剩下那块的号就被系统去掉——这一点不跟(他:「动态关闭后缀 1、2 很没道理」):
    关掉的屏用关掉那一刻的号(记账快照的名字里带着),亮着但此刻没被系统编号的屏用它上次的号(按显示器身份记),
    都没有或撞了就补最小的空号。系统重新编号(换口、重开后可能对调)时跟着系统走。同名只有一块时不编号,同系统设置。
    真机(2026-10-23):关掉一块后系统只剩一个不带号的「某型号」,面板仍是关着的 (2)、亮着的 (1);开回后与系统一致。
  - **尾号**:说明行写显示器自带序列号的尾号,如「外接 · 雷雳 3 · 序列号 …1A27 · 3840×2160 · 60Hz」(他的提议:「把唯一码放出来」),
    末 4 位,同组撞了就加长;关着的屏也写;读不到序列号就不写。号会随系统重新编号而变,尾号不变,认出是哪一台靠它。
  - **行序**按「基名 + 显示器身份」排(序列号文本,没有才 UUID),开关屏、系统改号、换接口都不跳。已关闭的屏重建菜单时清掉 `isMain`。
  - 改不了系统的名字:系统设置里没有改名入口(macOS 27 显示设置的本地化文本里没有「重命名」),显示器覆盖文件只能按厂商 + 型号改,
    同型号两台会被改成同一个名字。
  - 走过的弯(都在 2026-10-23):① 原先剥掉系统的号、按 UUID 自编号——UUID 随接法变,同一台换口后从 (2) 变 (1);
    ② 改按序列号自编号,号稳了却与系统设置对不上;③ 照抄系统的号再加尾号,号随开关忽有忽无;
    ④ 我把他「动态的后缀没道理」误读成「不要编号」,去掉了号,他指出对不上系统设置。最后:号同系统、不随开关消失,身份交给尾号与行序。

## 7. 安全保护规则与死锁安全模型

### 7.1 软件保护:机型感知,绝不陷入「无法恢复的全黑」

`DisplayController` 在执行「关闭」前强制校验 `canDisable(target, among: active, builtInFallback:)`,违反则拒绝(UI 上该行灰显):

- 关掉后仍剩 **≥1 块活跃屏** → 允许;
- 关掉后会变成 **0 块活跃(全黑)** → 仅当存在「**可开盖恢复的内建屏**」兜底才允许:
  - **有内建屏的机器**(笔记本,合盖、内建屏不活跃也算)→ **允许关到全黑**——开盖即可硬件恢复内建屏。满足「合盖用外接、关光外接、开盖恢复」的真实场景。
  - **无内建屏的机器**(Mac mini / Studio)→ **禁止**关最后一块活跃屏(无恢复路径)。

**死锁加固**:`builtInFallback` 只在内建屏面板存在**且未被本 app 软件关闭**时为真——被软件关掉的内建屏开盖也救不回,不算兜底。此外若 `target` 自身就是内建屏,关掉它后内建屏即被软件关闭,故也禁止把内建屏自己关成全黑。两者合起来堵死「软件关内建 + 关光外接 → 开盖救不回」的死锁。

「是否有内建屏面板」用 **`hasBuiltInDisplay()`** 判定:先看在线列表有无内建屏,再用「是否带内建电池」作便携机代理(合盖时内建屏不在在线列表);**检测不确定时保守按「无内建屏」处理**(宁可禁止全关,不冒险)。

### 7.2 死锁边界与逃生(2026-06-22 定稿)

§7.1 的加固已**主动堵死「纯软件」走到全黑**(软件关内建后不许再关光外接;也不许把内建自己关成全黑)。但软件**挡不住物理拔屏**,仍存在一个边界:

> **软件关掉内建屏 + 保留外接屏活跃,随后物理拔掉所有外接屏 → 0 块活跃屏 → 持续全黑。**

**已实验证伪「同进程内软件自动恢复」这条路:** 全黑发生时,显示子系统进入冻结态——`CGGetActiveDisplayList` 返回陈旧缓存(轮询失灵),`CGDisplayRegisterReconfigurationCallback` 的拔屏事件也不派发(回调失灵)。两条探测路径在最需要的那一刻同时哑火。因此「检测到拔屏再补救」的守护机制**不可靠,本期不做**(连同急救快捷键、IOKit 底层探测一并不做)。

**采用的逃生方案 = 强制重启,成立依赖两条硬不变量:**

1. **全程 `.forAppOnly`、绝不 `.permanently`**:进程一死(强制重启会杀掉它),系统自动回滚所有被关的屏 → 重启后显示配置必为正常。
2. **永不开机自启**:重启后 app 不会自己拉起,也就不会重新关屏 → 重启后必为「所有屏正常、app 未运行」的干净状态。

两条缺一不可。「永不开机自启」因此是**死锁逃生链条的一环、硬安全约束**,不是可选偏好——任何引入开机自启的改动都会破坏这条逃生路径,禁止。

> 取舍说明(2026-06-22 定稿):接受「死锁时短暂全黑、需强制重启」这一代价,换取实现的极简与可靠;不为一个边缘场景引入证伪过的不可靠守护。

**2026-09-07 更新 —— 这个取舍已被推翻,但上面关于 CoreGraphics 的结论反而被证实了。**

当天发生了一次真实事故:接外接屏 → 关内建屏 → 拔拓展坞 → 全黑,只能强制重启。事故场景与本节
预先写下的边界一字不差。据此重估:

- 它**不是边缘场景**,而是「接坞办公、拔坞走人」的日常动线;
- 本节对 CoreGraphics 的判断**完全正确**,当天拔线现场抓到的日志给出了原先缺失的数据(见 §7.3);
- 但「因此守护不可靠」这个**推论**不成立——当时只试了 CoreGraphics 的两条路,
  没有走内核事件这第三条。顺带一提,本节把 IOKit 探测也列进了不做清单,
  而 v1.0.3 修幽灵屏时早已引入并实测可靠,那条事实上已被推翻。

新的取舍见 §7.3。§7.2 关于「重启逃生」的两条硬不变量(永不开机自启、绝不 `.permanently`)**继续有效**,
救援是它之前的一道防线,不是替代。

### 7.3 全黑自动救援(2026-09-07,v1.0.7)

**判据与触发源都不碰 CoreGraphics**,因为当天在拔拓展坞现场实测到它在这件事上有两个硬伤:

| 信号 | 拔线瞬间的表现 | 可用性 |
|---|---|---|
| `CGDisplayRegisterReconfigurationCallback` | 拔线与插回**全程 0 次派发**(它只对配置变更如改分辨率派发) | ❌ 不可作触发源 |
| `CGGetActiveDisplayList` | 内核通知到达时仍报着拔线前的 3 块屏 | ❌ 不可作判据 |
| `physicalExternalCount()`(framebuffer 的 `Transport`+`DisplayWidth`) | 仍报 2 块,**滞后约 3.5 秒**才归零 | ❌ 救援用不了(菜单对账仍用它,那里不要求瞬时) |
| **带 EDID 的 `IOPortTransportState` 节点数** | **与内核通知同步,当场归零** | ✅ 判据 |
| **IOKit 服务终止通知** | **拔线瞬间抵达**(一次拔线派发 6 条) | ✅ 触发源 |

> v1.0.6 曾把救援建在 CoreGraphics 回调 + 活跃屏列表上,**实为死代码,一次也不会触发**;
> 上表前两行就是它的死因。这也是一次教训:验证「通路能通」(改分辨率时回调确实响)
> 不等于验证「真实场景会触发」——必须在真实触发场景下测。

**机制**:`IOServiceAddMatchingNotification` 挂 `kIOTerminatedNotification` 到 `IOPortTransportState`
基类,拔线时内核直接推送,**零轮询**。

> **机身 HDMI 口要多挂一种通知(2026-09-29 查明,v1.0.16 修复)**。这里原写着「一并覆盖 DisplayPort / HDMI」,
> 从未验证过,实测是错的:经拓展坞(USB-C / 雷雳)接的屏,传输节点随插线创建、随拔线销毁,终止通知能到;
> 机身 HDMI 口的节点 `Port-HDMI@1/DisplayPort` **常驻**(什么都没插时也在,`Active = No`),
> 拔线只是去掉它的 `EDID`、不销毁节点 —— **终止通知根本不会发**。当天首轮只拔 HDMI 与电源,一条通知都没有;
> 另两轮收到的通知,时刻都落在**同时拔掉的 USB 键盘**被移除的那一秒(晚于 HDMI 拔出 2–3 秒),与 HDMI 无关。
>
> 探针实测拔 HDMI 时内核实际发出的事件(两轮一致):终止通知 0 次;节点上的兴趣消息多条,
> **第一条早于 EDID 被去掉**(此刻判据还是 1);驱动随后**重新登记**这个节点,匹配通知(`kIOMatchedNotification`)
> 每轮来一次、排在最后,**到达时判据已归零**。于是再挂一条匹配通知,与终止通知共用回调。
> 它在插线和其他端口变化时也会来,回调只负责叫醒、判断交给救援判据,无害。
> 真机验收(v1.0.16,开着盖、屏幕醒着、只拔 HDMI,两轮):拔出后 **42 ms / 34 ms** 点亮内建屏,
> 期间无任何键盘 / 电源事件。这条依赖驱动内部行为,升级后用 `bash scripts/selfcheck.sh --plug` 动手复验。

> 为什么不用定时轮询:除了「轮询是猜不是机制」,还有实测原因——息屏时
> `CGGetActiveDisplayList` **会归零**(active 的定义含 awake),与全黑完全同形;
> 轮询分不清二者,会在用户息屏时擅自把他关掉的屏开回来。而息屏**不产生**任何拔线内核事件。

**判据**(P = 带 EDID 的外接屏数,D = 本 app 关掉的外接屏数):

```
P ≤ D  且  (内建屏也被本 app 关掉 或 这台机器没有内建屏面板)  →  判定全黑 → restoreAll()
```

对「拔掉的到底是哪一块」不敏感——而区分具体是哪块,正是做不到的事。查询失败返回 `nil` 时一律不动手。

**配套**:

- `restoreAll()` 只清**恢复成功**的记录:失败却照清等于把失败谎报成成功,屏还黑着、
  菜单里连那块屏都没了(双重失联);留着记录,重试才有意义。
- 有界重试 5 次 × 1 秒:全黑那一刻 WindowServer 正在收拾残局,配置调用可能被拒,
  而一旦拒了就没有第二次机会(屏已黑,不会再有拔线事件)。
- 诊断日志 `~/Library/Logs/DisplaySwitch.log`:全黑时用户看不到任何界面,
  救援若失败,现场会随强制重启一起消失。这是该路径唯一的黑匣子,只在救援事件时写。
  有上限 256 KB(实测每条约 110 字节、一个月约 100 条,约两年),超过只留最新的一半(他的要求:不能无限占空间)。
  每条都带判据实际取值——否则事后分不清「判据否决了救援」和「压根没进判断」。
  2026-10-22 起还记下**当时连着哪些外接屏接口**(传输节点路径,如 `Port-HDMI@1/DisplayPort`、
  `Port-USB-C@1/CIO/DisplayPort@0`)和**拔线通知是哪一种**(节点销毁 / 节点重新登记)——
  后者**不用来推断接法**,接法看接口路径。(曾据 10-22 一次拔坞写下「拓展坞拔线时最先到的是重新登记」;
  后从关机卡顿报告的内核栈查明,那次驱动早已卡死、拆除卡在 `terminatePhase1`,销毁通知根本发不出来,
  **那次测量不作数**。随后在驱动健康时按「前置检查 + 自动发现 + 自动恢复」复测(10-22 16:41,开盖、内建屏亮着):
  拔坞先到两条重新登记(第二条到时计数 2 → 0),2 ms 后到一条销毁——**「重新登记先到」在健康状态下成立**,
  这回证据是健康测量。同一次复测还给出一组**对照**:拔后 5 秒系统已正常拆掉两块外接屏(物理 0、活跃 0,
  无残影);而卡死那次同样的拔法,两块屏一直残留——**残影是驱动卡死的后果,不是拔法本身**。
  插回时会成串收到重新登记,且系统活跃屏数会比物理计数**早约 1 秒**恢复(活跃 2、物理 0→1→2),
  「物理 ≥ 活跃」这类检查不能在插线后头几秒里下判断。)
  9/29 查 HDMI 漏救援时,缺的正是这两条,只能靠事后翻系统日志猜。接口列表与外接屏计数同源,两者不会对不上。
  (思路借鉴 MonitorBar 读连接类型;它读的 `DFP Type Description` 在本机拓展坞下两路都只写 `DP`,
  分不出走的是哪条路,所以改用节点路径。)
- **两种时刻不硬试,等下一个时机**。判定集中在 `rescueDeferral()`,日志如实记下在等什么:
  - 只剩内建屏能救而盖子合着 → **等开盖**(2026-09-18:合盖时点亮内建屏会阻塞约 20 秒后失败)。
  - 屏幕在睡眠 → **等唤醒**(2026-09-29 加)。睡眠时系统把拔出事件推迟到唤醒才处理,
    此刻的配置调用会在主线程上忙等「上一次重配置完成」约 10 秒后失败——2026-09-22 睡眠中拔坞,
    两次救援各卡约 10 秒,一分钟刷出约 62 万行系统日志,进程被系统以日志量过大隔离;
    屏幕醒着时同样的调用 0.1 秒内完成(9/22、9/23、9/24 三次)。它挡的是**任何一块屏**的点亮,
    不像合盖只挡内建屏。判定问 WindowServer 自己(`CGDisplayIsAsleep`),在线屏**全部**报睡眠才算:
    误判成睡眠会把救援推迟到一次不会来的唤醒,误判成醒着只是退回空等,所以只在确定时才等。
  - 真机实测(2026-09-29,仅内建屏在线):睡眠通知到达时判为「睡」;按键唤醒时,产品的
    「开盖 / 唤醒」触发源被调用的那一刻已判为「醒」——推迟的救援在唤醒时一定会执行。
  - **真机验收通过(2026-09-29,v1.0.15,原事故机)**:外接屏走机身 HDMI、电源与 USB 键盘各自单独接
    (当天办公场景,**没有**走一线连的拓展坞)· 关内建屏 · 屏幕睡眠中拔线 → 按键唤醒:

    ```
    15:18:12  屏幕睡眠
    15:18:45  拔 HDMI —— WindowServer:「Deferred hotplugs cannot be processed in a non-wake state」
    15:18:47  拔线通知抵达(由同时拔掉的 USB 键盘触发,见上面「机制」的警示)
              | … | 瞬时外接屏=0 | 屏幕睡眠=true → 不硬试,等唤醒
    15:18:48  按键唤醒(Did Wake .853,随即处理推迟的拔出)→ 点亮内建屏(.871,18 ms 内完成),显示锁屏界面
    ```

    全程 0 条「Waiting for previous reconfig」(9/22 同一场景是约 62 万条、两次各空等约 10 秒)。
    同日还走了「合盖拔线 → 开盖」:拔线时判「等开盖」,开盖那一刻一次点亮。
    「等唤醒」这条逻辑与通知由谁触发无关;即使一条拔线通知都没有,唤醒触发源也会照常救援。
  - 同日首轮验收中一次合着盖拔线**没有留下任何记录** —— 已查明:那轮只拔了 HDMI 和电源,
    两者都不销毁传输节点,于是没有任何终止通知(见上面「机制」;v1.0.16 已修)。开盖时照常救回。

**真机验收(2026-09-07,原事故机 · 原动线)**,分两步做,第一步零风险先排掉致命前提:

1. 关掉一块**外接屏**后拔线(内建屏全程亮着):通知在真 app 进程(`LSUIElement` 后台程序,
   非命令行探针)抵达 3 次,`瞬时外接屏=0` 当场准确,**未误救援**。
2. 关掉**内建屏 + 一块外接屏**后拔线——比最简场景更难,拔线瞬间仍有 1 块外接屏物理连着,
   但那块正是被本 app 关掉的:

```
09:35:04  拔线通知抵达 | 本app已关屏=2(内建 1 / 外接 1) | 瞬时外接屏=1 | 有内建面板=true
09:35:06  已执行救援(剩余重试 5 次),当前活跃屏 1 块      ← 屏亮回来了
09:35:06  拔线通知抵达 | 本app已关屏=0 | 瞬时外接屏=0
09:35:06  判定无需救援,不动手                              ← 重复通知正确收手,幂等成立
```

判据 `P(1) ≤ D(1)` + 内建屏被关 → 正确判定全黑;**无重试记录**,即第一次配置调用就被系统接受——
印证了「在拔线瞬间动手、WindowServer 尚未进入冻结态」这一设计前提(那次是人在屏幕前操作;
屏幕睡眠时该前提不成立,见上面「等唤醒」)。至此
§7.2 遗留的最后一个未知(全黑那一刻点亮调用能否被接受)已消除。

## 8. 构建与分发

- **Swift Package Manager** 可执行目标,`swift build` / `swift run` 可构建运行。
- 打包脚本(`scripts/package.sh`)把产物包成 `.app`:生成 `Info.plist`(含 `LSUIElement = true`)、放入 bundle、本地开发者签名(ad-hoc)。
- 仅本地/自分发,不上架(用到私有 API,本就无法上架——与目标一致)。

### 发布门槛(2026-09-18 定,起因见下)

三层动作,门槛不同,**别混为一谈**:

| 动作 | 门槛 | 说明 |
|---|---|---|
| `commit` + `push` | 随时,不用问 | 工作记录,**允许中间态**。过程本身有价值,不该为了好看而攒着 |
| 打 `tag` | 值得回溯的点 | 便宜、可多打,不对外承诺任何东西 |
| 发 **release** | **必须真机验收通过** | 对外宣告「这个能用了」——公开、带永久记录、会被人下载 |

**起因**:2026-09-18 一天内发了 6 个 release,57 分钟内就发了 4 个,其中
v1.0.6 是从不触发的死代码、v1.0.9 引入了比原 bug 更隐蔽的回归、v1.0.11 与 v1.0.12 都没真正修好。
根子是把「发 release」当成了**完成的仪式**——发出去才觉得交付完了——
于是这个对外动作的门槛被降到了零。而真正的代价是:任何人(包括几个月后的自己)
打开 release 列表,会以为每一个都是有效里程碑,还可能下载到带回归的版本。

已按此清理:删掉那 4 个有缺陷的 release、**tag 全部保留**(git 历史不丢),
并给 v1.0.8 补上「只覆盖盖子开着的场景」的说明。

**判断「能不能发」的那句话**:这个版本我是否已经在真机、按用户的真实动线验证过?
没有 → 只 commit,不发。修 bug 尤其如此——今天的教训是
**「我以为修好了」和「真的修好了」之间,隔着好几个版本**。

## 9. 测试策略

- **单元测试(自动化)**:针对 `DisplayController` 纯逻辑——保护规则(机型感知:无内建屏剩 1 块拒关、有内建屏允许关到全黑、软件关内建后防死锁)、同型号屏的号同系统且不随开关消失、序列号尾号、按显示器身份排序、已关闭屏清主屏标记、`isSupported` 兜底、目标合法性——注入假 `DisplayInfo` 列表测试,不碰真实硬件。
- **Smoke / 真机走查(手动,需用户在场)**:真实开/关屏有硬件副作用,用脚本或打包后的 app 手动验证(列表/命名/关一块/最后一块灰显/关内建留外接/恢复)。所有涉及拔屏的实验须用户知情同意、人在现场、先存盘。
- 系统显示 API 调用集中在 `CGDisplayService` 一处薄封装,便于隔离。

## 10. 已知风险与缓解

| 风险 | 缓解 |
|---|---|
| 私有符号跨 macOS 大版本可能改名/失效;非 Apple Silicon 平台未验证 | `isSupported = 符号经 dlsym 可用 且 hw.optional.arm64==1`;任一不满足 → 菜单顶部提示「不支持」+ 各屏只读不可切换(`toggle` 亦早退)。便于适配,也保证不在未验证平台动屏 |
| 崩溃/异常残留黑屏 | `.forAppOnly` 系统自动回滚 + 启动时恢复 + 退出时恢复 |
| 关到 0 块活跃屏(无恢复路径) | `canDisable` 机型感知:无内建屏机器须留 ≥1 活跃屏;有内建屏机器允许关到全黑(开盖恢复),但内建屏已被软件关掉/target 本身是内建屏时禁止 → 纯软件不会陷入无法恢复的全黑 |
| **死锁:软件关内建 + 物理拔光外接 → 持续全黑** | 纯软件路径已被 §7.1 堵死;仅余物理拔屏边界 → **强制重启即恢复(`.forAppOnly` 回滚 + 永不自启);软件自动恢复已证伪,不做** |
| 「有无内建屏」检测不准 | `hasBuiltInDisplay`:在线列表 + 内建电池代理;不确定时保守按「无内建屏」(更安全,宁可禁止全关) |
| 显示器热插拔导致面板状态过期 | 面板每次弹出时重新枚举;开着时收到系统的屏幕参数变化通知即刷新(不轮询) |
| `displayID`、UUID 随重连 / 换口变化 | 持久标识用显示器序列号文本,没有才用 UUID;都不用 `displayID` |

## 11. 未来可扩展（均为本期非目标）

状态记忆、自动触发规则、虚拟屏创建、自定义命名(UUID 持久化、UI 文本可改)等,待本期稳定后按需另立设计。
